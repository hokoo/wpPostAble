# ADR 0002: wpPostAble 1.0 API freeze

- Status: Proposed
- Date: 2026-09-11
- Decision owner: Repository owner
- Delivery task: [T12 / issue #21](https://github.com/hokoo/wpPostAble/issues/21)
- Depends on: [ADR 0001](0001-versioning-and-release-strategy.md)

## Context

ADR 0001 approved the 1.0 compatibility boundary and feature scope. T9 through
T11 are now merged, tested, and independently verified. T12 must turn the
remaining historically observable surface into one precise PHP 7.4-compatible
contract before `1.0.0-rc.1`.

The audit found four choices that materially determine the 1.x compatibility
promise. They cannot be inferred from line coverage or resolved as formatting.

Known consumer evidence is conservative rather than exhaustive. Current heads
of `cf7-telegram`, `cf7-vk`, `neuralseo`, `cf7-slack`, `ct-antiscam`,
`ct-exchanges`, and `ct-treasures` use the trait initializer and public getters;
none calls `loadPost()`, overrides the initializer, directly accesses exception
context properties, or constructs the exceptions. Current primary consumers do
not access protected `$post`, but historical `cf7-telegram` code did, so stale
or private consumers may still depend on it.

## Decision gates

### Gate 1: interface return types

Recommended: fully align the interface with the trait wherever PHP 7.4 can
express the return contract. Add `getParam()` and `setParam()` to the interface;
use `self`, `string`, `array`, and `void` for the other exact contracts. Leave
only `getParam()` and `getMetaField()` natively untyped because their result is
`mixed|null` and native `mixed` requires PHP 8.

Alternative: add only `getParam()` and `setParam()` and preserve the legacy
untyped interface returns. This reduces immediate work for manual implementers,
but leaves the interface weaker than the documented trait throughout 1.x;
hardening it later would require 2.0.

Consequence of the recommendation: manual implementations and trait overrides
with missing return declarations must update before 1.0. Trait consumers without
overrides already satisfy the proposed types except for adding explicit `void`
to `deletePost()` and `setParam()`, which preserves their runtime null result.

### Gate 2: trait integration state and loaders

Recommended: keep `wpPostAble()` private as the required constructor-only trait
composition seam; keep `loadPost()` and `loadPostObject()` private implementation
details; make `$post` private and require `getPost()` for supported mutable
access. Remove the stale public `loadPost()` claim from README.

Conservative alternative: preserve `$post` as protected for 1.x and document
direct access as supported. This avoids breaking stale/private consumers but
commits the writable association property for the full major series. Widening
either loader to protected/public is not recommended because it creates a new
rebind/override contract without resetting all lifecycle state.

Consequence of the recommendation: code using `$this->post` or `$object->post`
must migrate to `getPost()`. Current primary consumer heads are already migrated;
the authorized private-consumer RC check remains mandatory.

### Gate 3: exception constructors and context properties

Recommended: preserve current public constructors, inheritance, non-final class
status, and public context-property existence through 1.x as legacy supported
surface. Recommend getters and constants for new code; direct mutation,
serialization shape, arbitrary manually constructed invalid state, and exact
message wording are not guaranteed.

Alternative: make context properties protected/private before 1.0 and require
getters. This improves encapsulation, but breaks published 0.x consumers and
possible subclasses for limited practical security benefit. It also expands
T12 migration and downstream risk without adding library behavior.

The frozen documentation must warn against serializing or logging raw exception
objects because their object graph may include post content, metadata, or
`WP_Error::error_data`.

### Gate 4: empty Core-result error codes

Recommended: when create/save returns an empty non-`WP_Error` result, synthesize
stable `WP_Error` codes `create_post_failed` and `save_post_failed` with minimal
post-type or post-ID context. Preserve an original Core `WP_Error` unchanged.

Alternative: retain and document the current blank-code fallback. This avoids a
pre-1.0 diagnostic change but contradicts the intended machine-readable error
contract and leaves consumers unable to classify the defensive failure path.

The recommendation changes only the defensive empty-result path. Existing Core
errors retain their original code, message, data, and identity.

## Proposed implementation after approval

- Align the 19-method interface and trait signatures with the approved PHP 7.4
  boundary and freeze parameter names used by PHP named arguments.
- Apply the approved initializer, loader, `$post`, exception, and fallback-error
  decisions without adding unrelated features.
- Add a reflection-driven public API/visibility/exception contract suite plus a
  manual interface implementation fixture on PHP 7.4 and 8.4.
- Extend package-install smoke to verify installed API signatures, not only
  symbol autoloading.
- Publish a complete API reference and a `0.7.x` to `1.0` migration guide;
  reconcile README, VERSIONING, TESTING, and CHANGELOG.
- Run full unit, 100% line/method coverage, package-install, localdev smoke, and
  WordPress minimum/latest verification followed by independent E3 QA.

## Out of scope

- Namespace or class renaming.
- PHP 8-only `mixed`, union, `static`, readonly, or asymmetric visibility types.
- A public reload/rebind API, parameter/meta deletion, or chainable `setParam()`.
- Hook, storage, or persistence redesign.
- Publishing `1.0.0-rc.1`; that remains the separate T13 owner gate.
